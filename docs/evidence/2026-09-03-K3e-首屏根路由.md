# K3e · 首屏根路由：reset 改到不带 modal 的 CardsHome

日期：2026-09-03
基线：`kuca/mobile-patches` @ `26580f659`（已含 K3b + K3c + K3d）

本车道不打包、不装机、不碰手机。真机「reset 到 Web 发出去了、JS 仍停在 Home」来自任务书已核实的 `gate-*` 记录。

## 要的结果、本轮不做

要的结果：冷启动最终是卡片流当根，栈里没有 Home 垫在下面。卡片页右上角「线程」把列表压上来，列表左上角原生返回回到卡片。

本轮不做：打包、装机、改 S1/S2、改 Web 的 `fullScreenModal`（单张卡片页和治理牌仍走原来的模态 Web）。

## 为什么选 (a)

真机记录只有一条：

```json
{"at":"2026-09-03T07:37:18.676Z","cardsFirstScreenEnabled":true,"decision":"apply","focusedRouteName":"Home","inboundLaunchTarget":false,"index":0,"preferencesLoaded":true,"reason":"untouched_home","routeNames":["Home"],"willDispatch":true}
```

门控条件全满足，`CommonActions.reset({ index: 0, routes: [{ name: "Web", params: { path: "/phone-cards" } }] })` 发出去了。之后 effect 没有因状态变化再跑，`report` 仍是 `route = Home`。同一进程里 `open-web` 用 `navigate("Web")` 立刻变成 Web——Web 作为压在 Home 上的模态可以，作为唯一根不行。

`Web` 在 `apps/mobile/src/Stack.tsx` 注册时带 `presentation: "fullScreenModal"`。native-stack 把这个 presentation 传给 `react-native-screens` 的 `stackPresentation`（不是 `push`）。把这样的屏 reset 成栈里唯一一页，JS 导航状态不会变成 Web。

所以换 reset 的目标，不换判定。新增 `CardsHome`：普通 push 屏，没有 modal presentation，内容复用 `PhoneWebRouteScreen`，路径钉死 `/phone-cards`。门控仍 `CommonActions.reset`，目标改成 `CardsHome`。单张卡片页、治理牌、自动化 `open-web` 仍走原来的模态 `Web`。

产品形状是 `["CardsHome"]`，点「线程」变成 `["CardsHome","Home"]`，再进线程是 `["CardsHome","Home","Thread"]`。这三态门控都不再 apply。不要 `["Home","Web"]`（卡片压在列表上，返回方向反了）。

## 为什么不是 (b)

K3b 说 `createStaticNavigation` 传不进 `initialRouteName`。核对了源码，这条仍然成立，而且就算能传，也消不掉启动后 reset。

`createStaticNavigation` 返回的组件把 props 转给 `NavigationContainer`，里面再渲染 `tree.getComponent()`。导航器自己的 `initialRouteName` 写在 `createNativeStackNavigator({ initialRouteName: "Home" })` 里，是模块加载时的静态值。返回组件的 props 类型里没有 `initialRouteName`。

`linking.config.initialRouteName` 可以传，但只影响 linking 的路径表默认项，不决定冷启动画哪一页。

`initialState` 可以传（`NavigationContainer` 的 rest props）。官方注释写明：传了 `initialState`，首次渲染不处理深链。K3c 要保住的冷启动 `["Thread"]` 就是 linking 的初始态，不能用这条路。

偏好是异步的。`RootStack` 建出来的时候还不知道开关。如果把静态 `initialRouteName` 改成 `CardsHome`，开关关掉的人会停在卡片流——门控在 `cards_first_disabled` 时 skip，没有反向把 CardsHome 换成 Home。

迟到的 `["Home","Thread"]` 恢复发生在启动之后。就算偏好已知时再挂导航器并把 `initialRouteName` 设成 CardsHome，这条恢复仍要一次启动后的 reset。K3c 的规则还在，(b) 替代不了门控。

所以 (b) 不能当本轮的动作。`initialRouteName` 仍是 `"Home"`，偏好打开时由门控 reset 到 `CardsHome`。

## 为什么不是 (c)

考虑过两条：

1. 去掉 Web 的 `fullScreenModal`，让 reset 到 Web 变成普通 push。单张卡片页和治理牌就不再是模态。从卡片流再 `navigate("Web", 单卡路径)` 会改同一条路由的 params，而不是压一层模态。
2. 按 path 动态改 Web 的 presentation。同一屏名既当根又当模态，native-stack 上不稳定；真机已经证明「把 fullScreenModal 的 Web 设成唯一根」这条路不通。

(a) 用两个屏名把两件事分开：根是 push 的 `CardsHome`，叠加是 modal 的 `Web`。这是 native-stack 上能讲得通的最小改动。

## 改了哪些文件

| 文件 | 做什么 |
| --- | --- |
| `apps/mobile/src/features/home/firstScreen.ts` | 目标屏从 `Web` 改成 `CardsHome`；`["CardsHome","Thread"]` 算 `restored_thread`；`["CardsHome"]` 算已经接管完 |

| `apps/mobile/src/features/home/CardsHomeRouteScreen.tsx` | 新屏。渲染 `PhoneWebRouteScreen`，路径固定 `/phone-cards` |

| `apps/mobile/src/features/home/firstScreen.test.ts` | 先改断言再改实现 |

K3c 规则没动：通知 / 自动化 / 快捷方式打 `inboundLaunchTarget` 就 skip；开关关掉 `route.name` 不是 `CardsHome`，reason 是 `cards_first_disabled`；`["Home","Thread"]` 仍 apply。K3d 的 `gate-*` 记录形状没动，主线仍靠它验。apply 成功之后应再有一条 `routeNames: ["CardsHome"]`、`reason: "not_a_launch_stack"` 的 skip。
