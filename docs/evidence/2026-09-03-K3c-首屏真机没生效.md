# K3c · 首屏卡片流在真机冷启动没生效

日期：2026-09-03
基线：`kuca/mobile-patches` @ `a866d4c39`（已含 K3b）

真机包：`com.example.kuca.dev`，jsbundle 含 `/phone-cards`。本车道不打包、不装机。

## 真机看到什么

冷启动（terminate + launch）后 20 秒发 `report`，当前路由是 Home。原件 `/tmp/k3b1-report.json`，`at` 为 `2026-09-03T05:11:38.361Z`：

```json
"route": { "name": "Home", "params": null }
```

当时目录已就绪，环境已连上，线程 105 条。偏好若没加载，Home 也可以作为导航状态存在；但 20 秒后仍停在 Home，说明 K3b 门控没有把根路由换成 Web。

再等约 54 秒发第二次 `report`，中间没有新的 boot 记录，也没有人碰手机。原件 `/tmp/k3b2-report.json`，`at` 为 `2026-09-03T05:12:32.826Z`：

```json
"route": {
  "name": "Thread",
  "params": {
    "environmentId": "kuca:<local-userdata>",
    "threadId": "4c98703e-248c-425c-bf99-c45711ca96c9"
  }
}
```

第二次环境相位从 `connected` 变成 `connecting`。线程 `4c98703e-…` 不在报告列出的前 40 条里，所以这不是列表第一项被误点，而是一条具体的上次线程被打开。

## 根因

K3b 门控在 `apps/mobile/src/features/home/FirstScreenGate.tsx`，判定在 `firstScreen.ts` 的 `shouldApplyFirstScreenRoute`：只在偏好已加载、目标是卡片、且栈恰好是 `["Home"]`、`index === 0` 时，才 `StackActions.replace("Web", { path: "/phone-cards" })`。

仓库里没有名为「恢复上次线程」的函数。冷启动把 Home 变成 Thread 的路径是普通的 `navigate("Thread")` / `linkTo("/threads/…")`，Home 留在栈底。对应坐标：

| 路径 | 文件 | 何时触发 |
| --- | --- | --- |
| React Navigation linking 的后续 URL | `App.tsx` 的 `linking` + `@react-navigation/native` `useLinking.native` | `getInitialURL` 150ms 超时后走 Home；之后 `url` 事件按 `threads/:environmentId/:threadId` 推出 Thread。自动化 URL 已被 `filter` 排除。 |
| 通知点开 | `apps/mobile/src/features/agent-awareness/notificationNavigation.ts` | `getLastNotificationResponse` 或监听器 `linkTo("/threads/…")`。原生 `lastResponse` 只活在进程内，纯 terminate 再 launch 一般是空的。 |
| 桌面快捷方式 | `apps/mobile/src/features/shortcuts/useAppShortcuts.ts` | `QuickActions.initial` 或监听器 `linkTo`。 |
| 自动化 `open-thread` | `apps/mobile/src/features/automation/automationLink.ts` | 这次两次 `report` 都不是这条。 |
| 用户点列表 | `HomeRouteScreen.tsx`、`AdaptiveWorkspaceLayout.tsx` | 需要手指。 |

`ThreadRouteScreen.tsx` 写明：深链冷启动会让 Thread 成为**唯一**路由。linking 的 initial state 就是 `["Thread"]`。自动恢复是启动之后再 navigate，栈是 `["Home", "Thread"]`。

K3b 把 `["Home", "Thread"]` 当成「深链或通知已经导航」，门控直接放手。这是 20 秒时仍在 Home、随后被上次线程抢走的判定错误。

另一处：Web 注册了 `presentation: "fullScreenModal"`。对根路由做 `replace("Web")` 不能稳定变成当前页。K3b 文档认为根路由会走 push 分支；真机 20 秒仍报 Home，说明 replace 没有成为 focused route。改成 `CommonActions.reset`，让 Web 成为栈里唯一的一页。

## 修法

1. `shouldApplyFirstScreenRoute` 在没有「这次启动已经有指定目标」时，也接管 `["Home", "Thread"]` 和 `["Web", "Thread"]`。`["Thread"]` 单独一页仍视为深链，不碰。从卡片进列表再进线程是 `["Web", "Home", "Thread"]`，也不碰。
2. 通知点开、自动化 `open-thread` / `open-web` / `new-thread`、快捷方式在 navigate 之前调用 `markInboundLaunchTarget()`。门控读到这个标记就放手。
3. 门控用 `CommonActions.reset` 把根路由设成 `Web /phone-cards`，不用 `replace`。

为什么这样不会把通知和自动化抢走：这两条会先打标记。linking 迟到的线程 URL 不打标记，按上次线程恢复收回。用户从卡片页点「线程」再点一条，栈长度是 3，门控不收。
