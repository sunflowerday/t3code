# K3d · 首屏门控诊断：每次判定写成可拉取记录

日期：2026-09-03
基线：`kuca/mobile-patches` @ `872dc205b`（已含 K3b + K3c）

本车道不打包、不装机、不碰手机。真机冷启动仍停在 Home 的事实来自任务书已核实条目，原件 `/tmp/k3c1-report.json`、`/tmp/k3c2-report.json`、`/tmp/boot-latest.json`。

## 本轮做了什么

门控每次 effect 跑到，只要自动化已开，就往 App 容器 `Documents/automation/gate-<时间戳>.json` 写一条判定。主线打包装机后，冷启动 20 秒拉这些文件，就能看见门控当时看到的栈、偏好、入站标记，以及它为什么 apply 或 skip。

本轮**没有改导航动作**。K3c 的 `CommonActions.reset` 仍在。从代码上还不能单独钉死真机停在 Home 的那一条原因，见下面「最可能的原因」。

## 真机已经看到什么（样本量 2 次 report + 1 次 boot，不是空集）

冷启动（terminate + launch）。boot 记录 `initialUrl: ""`，`at` 为 `2026-09-03T07:14:38.409Z`。

20 秒后 `k3c1` report，`at` 为 `2026-09-03T07:15:01.764Z`：

```json
"route": { "name": "Home", "params": null }
```

目录已就绪，线程 105 条。环境相位当时是 `reconnecting`。

约 80 秒再 `k3c2` report，`at` 为 `2026-09-03T07:16:06.732Z`：仍是 Home。环境已 `connected`，线程 106 条。这次没有像 K3c 修之前那样跳到上次线程。

随后发 `open-web?path=/phone-cards`，report 变成 `Web` + `path:"/phone-cards"`。Web 屏和卡片页本身正常。只有冷启动自动接管没发生。

## 记录长什么样

文件名：`Documents/automation/gate-<时间戳>.json`。

只在 `isAutomationArmed()` 为真时写。`.dev` 包名直接算已开；否则看 `Documents/automation/ARMED` 文件。和 `automationNote` 同一套写文件函数。

一条记录的字段：

| 字段 | 含义 |
| --- | --- |
| `at` | 这次 effect 跑到的时间 |
| `routeNames` | 根栈屏幕名 |
| `index` | 当前下标 |
| `focusedRouteName` | `routeNames[index]`，方便和 automation `report` 的 `route.name` 对 |
| `preferencesLoaded` | 偏好 atom 是否已经 Success |
| `cardsFirstScreenEnabled` | 卡片首屏是否开（没选过则默认开） |
| `inboundLaunchTarget` | 通知 / 自动化 open-* / 快捷方式是否已打标 |
| `decision` | `apply` 或 `skip` |
| `reason` | 见下表 |
| `willDispatch` | 是否马上 `CommonActions.reset` 到 `Web /phone-cards` |

`reason` 取值：

| reason | decision | 何时 |
| --- | --- | --- |
| `untouched_home` | apply | 栈恰好是 `["Home"]` 且 index 0 |
| `restored_thread` | apply | 栈是 `["Home","Thread"]` 或 `["Web","Thread"]` |
| `preferences_not_loaded` | skip | 偏好还没 Success |
| `cards_first_disabled` | skip | 目标不是 Web（开关关了） |
| `inbound_launch_target` | skip | 进程内入站标记已打 |
| `inbound_thread_only_stack` | skip | 栈恰好是 `["Thread"]`（深链初始态） |
| `not_a_launch_stack` | skip | 其余，包括门控自己 reset 出来的 `["Web"]` |

坐标：

- 判定：`apps/mobile/src/features/home/firstScreen.ts` 的 `describeFirstScreenDecision` / `buildFirstScreenGateRecord`
- 写文件：`apps/mobile/src/features/automation/automationLink.ts` 的 `writeFirstScreenGateRecord`
- effect：`apps/mobile/src/features/home/FirstScreenGate.tsx`

主线拉到记录之后，按下表读：

| 看到的记录 | 含义 |
| --- | --- |
| 一个文件都没有 | 门控 effect 没跑，或自动化没开（`.dev` 包不应发生） |
| 只有 `skip` / `preferences_not_loaded`，没有后续 | 偏好没 Success，或者 Success 之后 effect 没再跑 |
| `skip` / `cards_first_disabled` | 设备上开关是关的，停在 Home 是对的 |
| `skip` / `inbound_launch_target` 而 report 仍是 Home | 入站标记被误打，且那次 navigate 没离开 Home |
| `apply` / `untouched_home` 且 `willDispatch: true`，之后没有 `["Web"]` 的记录，report 仍是 Home | reset 发出去了，JS 栈没变成 Web |
| `apply` 之后出现 `routeNames: ["Web"]` + `skip` / `not_a_launch_stack` | reset 成功了；若 report 仍是 Home，是报告读的 route 和栈不一致 |

## 真机可能走到的路径

冷启动默认栈是 `["Home"]`。`RootStack` 的 `initialRouteName` 是 `"Home"`（`apps/mobile/src/Stack.tsx`）。linking 的 `filter` 丢掉自动化 URL（`apps/mobile/src/App.tsx`）。这次 boot 的 `initialUrl` 是空字符串，linking 不会在启动时推 Thread 或 Web。

门控挂在 `RootStackLayout` 里，和 `AdaptiveWorkspaceLayout` 平级。偏好没 Success 之前，布局渲染 `null`，门控自己已经挂上了。splash 隐藏的条件是同一个 `mobilePreferencesAtom` Success 且不在 waiting（`apps/mobile/src/features/settings/appearance/AppearancePreferencesProvider.tsx`）。人能看见 Home、自动化能 `report` 的时候，偏好几乎一定已经加载完。这只能说明 20 秒那个瞬间 `preferencesLoaded` 应为 true；**第一拍** effect 仍可能先 skip 再在 Success 后 apply。

`inboundLaunchTarget` 进程内默认 false。会把它打成 true 的只有三条，而且打标后立刻 navigate / `linkTo`：

| 路径 | 文件 | 冷启动这次会不会打 |
| --- | --- | --- |
| 自动化 `open-thread` / `open-web` / `new-thread` | `apps/mobile/src/features/automation/automationLink.ts` | 不会。boot 的 initialUrl 为空；`report` 动作不打标 |
| 通知点开 | `apps/mobile/src/features/agent-awareness/notificationNavigation.ts` | 一般不会。原生 lastResponse 只活在进程内；真打了也会 `linkTo` 离开 Home |
| 桌面快捷方式 | `apps/mobile/src/features/shortcuts/useAppShortcuts.ts` | iPhone 冷启动通常没有 `QuickActions.initial`；真有也会 `linkTo` |

所以「标记被误打、人还停在 Home」需要打标成功、导航失败。代码上看不到这样的冷启动路径，但不能在单测里证伪，要靠记录里的 `inboundLaunchTarget`。

上次线程自动恢复：仓库里没有单独的「恢复上次线程」函数。K3c 观察到的是启动后 linking 迟到的 `threads/…` URL，栈变成 `["Home","Thread"]`。这次 80 秒仍是 Home，说明这条迟到 URL 这次没来。它解释不了「停在 Home」，只解释「为什么这次没被线程抢走」。

用户点列表才会 `navigate("Thread")`（`HomeRouteScreen.tsx`、`AdaptiveWorkspaceLayout.tsx`）。这次没人碰手机。

## 最可能的原因

**reset 把 Web（`presentation: "fullScreenModal"`）设成栈里唯一一页，JS 导航状态没有变成 Web。**

为什么这么排：

1. K3b 对根路由 `StackActions.replace("Web")`。20 秒后 automation `report` 仍是 Home。`getCurrentRoute()` 读的是 JS 状态，所以不是「原生还画着 Home、JS 已经是 Web」。
2. K3c 改成 `CommonActions.reset` 到只有 Web。装机后再冷启动，20 秒和 80 秒仍是 Home。同一种失败。
3. 同一进程里发 `open-web`（内部是 `automationNavigationRef.navigate("Web", …)`），立刻变成 Web。navigate 是把 modal Web **压在 Home 上面**，不是把 Home 换成 Web。
4. K3b 文档认为 `RNSScreenStack` 会把栈里第一页当 push，modal 对根无效。真机两次改写根路由都没让 JS 的 focused route 变成 Web，这个假设至少对「已经存在的 Home 根再改写成 Web」不成立。

排在后面、要靠记录排除的：

- 设备上「首屏显示卡片流」被关掉。停在 Home 就是对的。设置页开关在 `apps/mobile/src/features/settings/SettingsRouteScreen.tsx`。
- 第一拍 `preferences_not_loaded` 之后 effect 没因 Success 再跑。和 splash 用同一个 atom，可能性低。
- `inboundLaunchTarget` 误标。上面三条打标路径都会离开 Home。

不能在这一轮下修：要换的动作会改栈形状。K3b 明确不要 `["Home","Web"]`（卡片压在列表上，返回键方向反了），要的是根是 Web、列表再压上去。在记录证明 reset 确实发出去且 JS 仍是 Home 之前，改成 navigate 或改 Web 的 presentation，都是在猜产品形态。

## 单测能复现什么、不能复现什么

能。判定和记录形状是纯函数，已补在 `apps/mobile/src/features/home/firstScreen.test.ts`：

- `describeFirstScreenDecision` 覆盖全部 7 个 reason
- `buildFirstScreenGateRecord` 锁 `routeNames` + `decision`，以及 skip 时 `willDispatch: false`

这不是「先红后绿修真机 bug」。这是把门控判定的原因变成可断言的输出。旧的 `shouldApplyFirstScreenRoute` 15 条行为锁没改。

不能。native-stack 是否接受「把 fullScreenModal 的 Web 设成唯一根」发生在 `react-native-screens` 里。node 单测没有那个栈。`FirstScreenGate.tsx` 的 dispatch 本身也没有 RN 测试环境。所以「reset 发出去了但 report 仍是 Home」这一条，只能靠真机 `gate-*` 记录对上后续 `report`。
